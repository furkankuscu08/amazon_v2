# Draft quality evaluation for synthetic consultation routing

This is a small, curated development benchmark, not a specification of organizational ownership or proof of general model quality. The input is the synthetic idea “We want to streamline how retail campaign audiences are signed off before launch.” `tests/fixtures/quality_baseline.json` contains only sanitized, locally validated area IDs, search intents, retrieved visible record IDs, role proposals, and observed card roles from one live HTTP run on 27 September 2026. Five borderline role labels were adjudicated by the user; the remaining straightforward labels are evidence-grounded draft judgments. It does not contain raw provider replies, confidential records, or a claim that another model run would return the same card.

## Role rubric

- `direct_contact`: a visible, current duty explicitly covers this area's consultation need, or a visible work trace connects the person through hands-on work **on that need**. A cross-team direct contact is valid with area-specific evidence; the person's org label alone neither grants nor bars the role.
- `advisor`: visible hands-on work on an adjacent or historical process, or a current visible responsibility, can support a narrow question about that work or duty without implying ownership of a different process, approval authority, or subject expertise. A thin but explainable visible link is acceptable here when the question can be grounded in what the source actually shows.
- `none`: do not propose when the only connection is a title, `mention`, unrelated subject, restricted source, or a role whose scope cannot be explained from the visible record. A routing contact separately requires current visible manager and team remit evidence and is inappropriate when a suitable direct contact exists.

## Implemented role contract and its limits

Each area now carries a `consultation_need` (what that area must know or decide for this idea), and each proposed person names one `primary_evidence_id` and a `relevance` of `direct`/`adjacent`/`weak`. The deterministic audit uses these to require that a `direct_contact` has a strong work or current-responsibility tie on its **single primary** citation, so a weak tie on the relevant record can no longer borrow strength from an unrelated record in the same list. When the model itself marks the link `adjacent` or `weak`, the contact is kept as an `advisor` rather than dropped or asserted as direct, matching the product decision that an explainable but thinner contact should remain visible instead of becoming `not_found`. `mention`-only evidence is not proposed, and an area with no supportable person still becomes `not_found`; a contact in every area is not a goal. These checks verify visibility and link strength only. A visible source can still be on-topic-looking yet wrong for the area (for example the Platform checklist assignee), so area-specific semantic relevance remains unverified. The interview question is likewise guided by the prompt to stay within what the source shows, but a question can still end in `?` while asserting an unsupported premise (the privacy-run example); the deterministic checks confirm only format and no leaked IDs. No source-agnostic semantic threshold or embedding change has been added.
- `null` in `expected_role`: a future role needing human adjudication; it is displayed but excluded from scores. All 17 current baseline cases are labeled. Absence of a proposal is represented by `"none"`, not `null`.

Each case names the consultation need separately from the model's wording. A visible record is not automatically relevant just because BM25 or Qdrant retrieved it. Before finalizing a role, check that the cited record describes the particular consultation need, whether the person is its author/assignee rather than merely mentioned, and whether a historic process still applies. A question about an unknown requirement is acceptable; asserting that the requirement already exists is not.

## Replay and current baseline

Run `uv run --python 3.12 --no-project --with-requirements requirements.txt python -m scripts.quality_eval` from the repository root. The replay seeds a temporary SQLite database, checks that captured records and reference sources are visible, reconstructs directory candidates, and submits normalized recorded role/evidence proposals to the real `audit_area` logic. The normalization uses a fixed safe question and confidence because the snapshot records role and citation decisions rather than raw model text, and the recorded proposals predate the `primary_evidence_id`/`relevance` contract, so those two fields are reconstructed from the captured role and citations rather than original model output. The output distinguishes reference availability (a work source was in the captured retrieval set, or a directory source was visible), candidate availability, the model's role, the audited role, and cases that need adjudication; it also reports whether replayed roles match the observed card. This is not an actual rerun of BM25, Qdrant, `impact`, `priority`, or OpenRouter.

The 17 examples are labeled, including five user-adjudicated borderline decisions. Eight expect a person; all eight reference sources and candidates are available. Ten of 17 model roles and 12 of 17 audited roles match the labels. Six model `direct_contact` proposals lack area-specific direct support; the deterministic audit catches two reporter-only proposals but accepts four overclaims, including Platform's checklist assignee. These are **counts on hand-picked examples**, not precision/recall estimates or proof of broad model quality. Three more synthetic ideas have separate, narrower one-run observations and do not contribute to these counts.

## Adjudicated borderline cases

- **Jules / Growth → `advisor`:** The visible current duty is campaign launch approval review, not explicitly audience sign-off. The last card chose `direct_contact`.
- **Nina / Brand → `advisor`:** Her audience checklist can inform a question about checklist steps, not prove Brand review authority. The last card chose `advisor`.
- **Owen / Platform → `advisor`:** His scheduler/platform API integration update supports advice about technical constraints, not ownership of an approval workflow. The last card chose `direct_contact`.
- **Nina / Commerce → `advisor`:** Her retail launch coordination can inform cross-team consultation, not establish a Commerce Operations duty. The last card chose `direct_contact`.
- **Priya / Commerce → `none`:** Her previous team's 2023 campaign approval document does not establish a Commerce operations connection. The last card chose `advisor`.

The already-coded visibility fix is different: a title-only directory candidate with no visible evidence could have leaked a restricted-only person to model context; no role judgment is needed to reject that path. No semantic relevance gate has been added based on this single card.

The Jules adjudication also exposed a narrower role-policy mismatch: previously, `audit_area` accepted a current visible responsibility for `direct_contact` but not `advisor`, making the approved `advisor` role impossible when that is the only citation. It now accepts a current visible responsibility for an advisor's duty-scoped question, while continuing to reject expired/restricted duties and manager/remit-only advisor evidence. This is an offline-tested code correction **after** the live cards below; the recorded live outputs have not been regenerated with the updated prompt or audit. The baseline replay still records the historical model proposal of `direct_contact` and therefore still counts it as a mismatch.

## Additional live scenarios and next evaluation

- The user approved three distinct synthetic English reference ideas: scheduler/platform API integration, reassessment of the previous team's campaign review process, and privacy-review abstention. Each was then run **once** through the live HTTP flow with the same pinned OpenInference endpoint and current synthetic fixtures. The server produced valid, reloadable cards in about 111 s (five total model calls; 7,186 total tokens), 125 s (six calls; 11,743 tokens), and 90 s (six calls; 8,510 tokens), respectively; no clarification was requested. These are provider-reported token counts, not verified billed costs. At most two area calls overlapped in each run. Cited source links opened, restricted source links returned 404, and no restricted-only candidate reached the model. Different idea complexity and completion lengths prevent a controlled latency comparison.
- In the integration case, the target Platform area retrieved `github:campaign-scheduler-76` through BM25 and displayed its author Owen as `direct_contact`, matching the approved reference; the checklist author was not added to that Platform area. An additional Growth area took about 79 s and 2,173 completion tokens, dominating total latency. The Platform question contained the awkward truncated phrase “this re-?” despite valid JSON and a normal finish reason, so syntactic validation alone does not guarantee useful question wording.
- In the historical-process case, the target Brand area retrieved `docs:campaign-review-2023` and displayed its author Priya as `direct_contact`, **not** the approved `advisor` reference. The document describes a previous team, and its author link alone does not establish current review authority; the model chose a stronger role than the approved one, while the deterministic audit checks link type rather than this semantic distinction. The model also proposed extra Growth, Platform, and Commerce consultation areas; their subject-specific quality was not scored in this target-area comparison.
- In the privacy case, the target Security area was `not_found` with no person, as expected from a fixture with no visible privacy-duty evidence. A separate Commerce area asked Nina about customer-data terms supposedly captured in the audience checklist, although `jira:MKT-482` only describes a task to finalize the checklist. This is an unsupported question premise, not evidence of a privacy review duty. All four specified hard-negative people were absent from their target areas across the three cases; this does not certify unscored extra areas.
- `tests/fixtures/quality_scenarios.json` stores only normalized target-area observations, visible source IDs, access checks, and durations. `scripts/quality_eval.py` can verify their references and compare target roles (one of two positive roles matched; the no-contact Security case matched) **without making live calls**. It cannot reproduce the original `impact` decisions, semantic vector retrieval, model text, or full card from those observations. Do not count this as an independent model run.
- Evaluate `impact` area/mapping, retrieval of labeled relevant records, candidate availability, model role decisions, and audit decisions as separate stages. Keep `mapping_unresolved`, `not_found`, `review_incomplete`, and request-level refusal distinct; preserve the restricted-source zero-leak criterion and the two-call per-request bound.
- Before changing a semantic guard or role prompt, expand the label set beyond this campaign-focused fixture and inspect additional full stage traces; the current evidence shows repeated overclaims, not a validated threshold. Only after the user explicitly approves further paid calls, run a focused comparison with the same provider and synthetic ideas, report token use/latency and variation, and stop to diagnose failed calls rather than blindly retrying. Do not migrate embeddings from this small set.
