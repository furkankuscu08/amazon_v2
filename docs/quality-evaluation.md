# Draft quality evaluation for synthetic consultation routing

This is a small, curated development benchmark, not a specification of organizational ownership or proof of general model quality. The input is the synthetic idea “We want to streamline how retail campaign audiences are signed off before launch.” `tests/fixtures/quality_baseline.json` contains only sanitized, locally validated area IDs, search intents, retrieved visible record IDs, role proposals, and observed card roles from one live HTTP run on 27 September 2026. Five borderline role labels were adjudicated by the user; the remaining straightforward labels are evidence-grounded draft judgments. It does not contain raw provider replies, confidential records, or a claim that another model run would return the same card.

## Role rubric

- `direct_contact`: a visible, current duty explicitly covers this area's consultation need, or a visible work trace connects the person through hands-on work **on that need**. A cross-team direct contact is valid with area-specific evidence; the person's org label alone neither grants nor bars the role.
- `advisor`: a visible work link (including a reporter who can explain the reported task) or a current visible responsibility can support explaining a related real process or work item, helping understand this area's need or approach the appropriate practitioner. Area expertise is not required, but the source-to-need bridge must be explainable; merely sharing a project word is insufficient. Do not imply ownership, approval authority, undocumented process contents, or that the person is known to know the correct practitioner. Manager/remit-only evidence still supports routing, not an advisor role.
- `none`: do not propose when the only connection is a title, `mention`, unrelated subject, restricted source, or a role whose scope cannot be explained from the visible record. A routing contact separately requires current visible manager and team remit evidence and is inappropriate when a suitable direct contact exists.

## Implemented role contract and its limits

Each area now carries a `consultation_need` (what that area must know or decide for this idea), and each proposed person names one `primary_evidence_id` and a `relevance` of `direct`/`adjacent`/`weak`. The deterministic audit uses these to require that a `direct_contact` has a strong work or current-responsibility tie on its **single primary** citation, so a weak tie on the relevant record can no longer borrow strength from an unrelated record in the same list. When the model itself marks the link `adjacent` or `weak`, the contact is kept as an `advisor` rather than dropped or asserted as direct, matching the product decision that an explainable but thinner contact should remain visible instead of becoming `not_found`. `mention`-only evidence is not proposed, and an area with no supportable person still becomes `not_found`; a contact in every area is not a goal. These checks verify visibility and link strength only. A visible source can still be on-topic-looking yet wrong for the area (for example the Platform checklist assignee), so area-specific semantic relevance remains unverified. The interview question is likewise guided by the prompt to stay within what the source shows, but a question can still end in `?` while asserting an unsupported premise (the privacy-run example); the deterministic checks confirm only format and no leaked IDs. No source-agnostic semantic threshold or embedding change has been added.
- `null` in `expected_role`: a future role needing human adjudication; it is displayed but excluded from scores. All 17 current baseline cases are labeled. Absence of a proposal is represented by `"none"`, not `null`.

Each case is judged against its run's actual generated consultation need. Retrieval alone does not establish relevance: direct support requires work on that need; advisor support requires an explainable contribution from a related real process. A historical author may be direct for a need about that historical work itself, without proof of current authority. Judge contact usefulness, direct support, and question premises separately: a useful advisor may still have an unsupported original question, and a safe question does not make an unrelated person useful. Open questions about whether a requirement exists or what would matter are acceptable; asserting that the requirement already exists is not. Impact receives the idea and org inventory, not work records, so a plausible conditional consultation hypothesis is not automatically false because it is absent from the idea or retrieved sources.

## Replay and current baseline

Run `uv run --python 3.12 --no-project --with-requirements requirements.txt python -m scripts.quality_eval` from the repository root. The replay seeds a temporary SQLite database, checks that captured records and reference sources are visible, reconstructs directory candidates, and submits normalized recorded role/evidence proposals to the real `audit_area` logic. The normalization uses a fixed safe question and confidence because the snapshot records role and citation decisions rather than raw model text, and the recorded proposals predate the `primary_evidence_id`/`relevance` contract, so those two fields are reconstructed from the captured role and citations rather than original model output. The output distinguishes reference availability (a work source was in the captured retrieval set, or a directory source was visible), candidate availability, the model's role, the audited role, and cases that need adjudication; it also reports whether replayed roles match the observed card. This is not an actual rerun of BM25, Qdrant, `impact`, `priority`, or OpenRouter.

The 17 examples are labeled, including five user-adjudicated borderline decisions. Eight expect a person; all eight reference sources and candidates are available. These are **counts on hand-picked examples**, not precision/recall estimates or proof of broad model quality. Three more synthetic ideas have separate, narrower one-run observations and do not contribute to these counts.

## Area-prompt intervention (30 September 2026; no live comparison yet)

`PROMPTS["area"]` in `workbot/llm.py` now organizes the decision as primary-source facts → personal link → useful contribution to this run's consultation need → role. Direct requires personal work on the specific need on the primary source; an advisor can explain related real work/process or a current duty without area expertise, provided the contribution is explainable. Reporter-level explanation is not ownership, manager/remit remains routing-only, and historical work is not automatically downgraded when the need concerns that work. The question instructions distinguish open inquiry from presumed controls, findings, or source contents; the source need not already contain the answer. No reasoning narrative or new response field is requested.

Only the area prompt, related request/response tests, and documentation changed. Impact/priority prompts, schemas, retrieval, candidate selection, audit, neutral card questions, provider/model/reasoning/token settings, synthetic sources, captured observations, and labels remain unchanged. There is no new verifier, retry, semantic threshold, or automatic role conversion. The audit still cannot independently verify area-specific semantic relevance. Token-cap failures from the experimental runs remain a separate unresolved issue; this intervention does not establish a fix for them.

`tests/test_llm.py` uses a synthetic staging-release payload and mocked HTTP responses to check instruction coverage, payload preservation, the existing schema/provider settings, successful parsing, empty replies, and rejection of truncated/malformed/invalid replies without retries. These checks establish request/response behavior, **not that a model obeys the prompt or that contact quality improved**. Diagnostic and audit replay of the older captured proposals should remain unchanged; they do not run this new prompt.

A live comparison is **pending and requires separate explicit approval** of the provider and call/cost budget. Its design should hold the idea, clarification answers, generated area need, candidate order/evidence, request settings, and current audit fixed while comparing old/new area prompts. Choose a small mix of established failure cases and fresh synthetic references before seeing outputs, repeat both arms, and retain observations and labels separately from existing fixtures. Measure unsupported model/card direct claims, useful person plus acceptable primary coverage, supported direct retention, original-question premises, malformed/empty/truncated responses, latency, and available token usage independently; exclude pending labels only from the relevant denominators. Do not silently change provider if the pinned endpoint is unavailable. Retain the prompt only if fewer overclaims do not come at the cost of losing useful advisors or supported direct contacts; any explanation-field, retrieval, or token-budget intervention is a separate later decision.
