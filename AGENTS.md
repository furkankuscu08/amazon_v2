## Product and language boundaries

- WorkBot is a **synthetic, simulated Alexa+ web experience**, not an official Alexa+ or Amazon API integration. It shows consultation areas, evidence-backed people and roles, questions to ask, and uncertainty; it does not send messages, create invitations, or record coordination.
- Do not claim real identity or permission controls, production security or scale, or exhaustive stakeholder discovery. Preserve visibility checks: restricted sources and people known only through them must not enter accessible search, model context, cards, source views, or user-visible signals.
- Preserve the three model task types (impact, per-area evaluation, card-wide priority) and at most two sequential clarifications. The priority call orders areas and may pick up to four already-audited people to talk to first; it must never add a person or change a role. A missing or over-long choice is tolerated so it cannot discard the area order. Keep `mapping_unresolved`, `not_found`, `review_incomplete`, and request-level refusal distinct.
- **English is the WorkBot operational language.** Write demo ideas and clarification answers, synthetic work records, search intents, model prompts and requested responses, UI copy, and displayed questions/cards in English. Keep `README.md` and this file in English. This is a product convention, **not** a claim that the application detects or rejects other languages at runtime. Report to the user in Turkish unless told otherwise.
- Use synthetic inputs only. Never include `.env` secrets in code, logs, tool output, or commits. Live OpenRouter calls transmit prompts and incur cost; run them only when the user explicitly approves a live test and its budget, and distinguish their results from offline tests. Submitting an idea through the web UI is a live call.

## Repository map

`workbot/` is the application package, `tests/` contains offline regression tests, and `docs/` holds the handoff, the design draft, and competition research.

- `compose.yaml` runs local Qdrant and, optionally, the app; `.env.example` is the configuration template. `requirements.in` lists direct dependencies; `requirements.txt` is the compiled Python 3.12 lock.
- `workbot/main.py`: FastAPI routes and the server-rendered flow. `POST /sessions` and `POST /sessions/{sid}/answer` store the request, start the workflow on a background thread with its own database connection, and redirect at once; the session page shows progress while the state is `processing`. Only a newly created session starts a run, so a repeated idempotency key cannot start a second one.
- `workbot/models.py`: strict structured-output models. Each `Area` carries a `consultation_need`; each `PersonProposal` carries a `primary_evidence_id` (must be one of its citations), a required 5-600-character `contribution` (the prompt asks for under 250; the cap is higher so a provider enforcing it does not cut a sentence), and a `relevance` of `direct`/`adjacent`/`weak`. The model writes no question or caution text for a person. The direct-contact evidence requirement lives in the audit, not the schema, so one inconsistent role field cannot void a whole area review.
- `workbot/service.py`: session orchestration, all of an idea's per-area model calls at once (six worker threads), the deterministic evidence audit, card states, and the in-memory progress shown on the waiting page. Progress may hold only a stage and area labels with a done flag, never people, sources, counts, or diagnostics. A live run has a progress entry from before its session becomes `processing` until after it leaves that state; the session page relies on this to close a `processing` session without one as a refusal, so keep that ordering. Keep SQLite/search/permission reads and audits on the thread that runs the workflow; only independent area model requests belong in workers. Wait for all areas before the priority call, keep area failures isolated as `review_incomplete`, and check the shared question before reordering so a guard error leaves the original order intact. A `direct_contact` needs `relevance=direct` plus a strong work or current-responsibility tie on the single primary source; `adjacent`/`weak` proposals are kept as advisors; `mention`-only evidence is not proposed; a routing contact needs both current manager and visible remit evidence and is hidden when a direct contact exists or was rejected. The audit verifies visibility and link strength, **not** whether the source is semantically relevant to the area. The card shows the model's `contribution` labelled as an unverified model summary, trimmed to complete sentences and hidden when it has none or contains a URL, email address, or source ID. Neither it nor the `ended_duty` note and its `context_ids` may be passed to the priority call. The question and caution on the card are WorkBot's own: a neutral question from `workbot/questions.py` and a fixed caution. A skipped clarification ends the question budget. The audit also attaches an `ended_duty` note when an accepted person has a visible responsibility that has ended and shares a word with the area, unless they hold a current one that also does; the model never sees expired duties, and the note's source is listed in `context_ids` so the dependency snapshot fails the card closed if that source changes or stops being visible. A routing contact's plan line states that no one with visible work was found, or that no direct contact was established when an advisor is shown in the same area. Never place diagnostic or rejection details in the card passed to priority.
- `workbot/search.py`: visible BM25/Qdrant retrieval fused by reciprocal rank, keeping per intent only records both channels returned plus each channel's top three (at most eight per area), and candidate selection from work links, current visible responsibilities, and manager plus remit. The ten work-link candidates are chosen by link strength and then by the retrieval rank of their best record; mention-only people are not work candidates. A title match without visible evidence must not expose a restricted-only person to model context.
- `workbot/questions.py`: the four shared neutral English questions, with no model/schema/DB imports.
- `workbot/plan.py`: pure functions that turn a stored card into the short plan at the top of the page. Each person gets one home area (where their role is strongest; between equal roles, their own team's area); the plan lists the priority call's `first_conversations` or, without a usable choice, the strongest person of each area; other areas show a one-line cross-reference. It is computed at render time and must tolerate older cards without `org_id`, `team`, `primary_kind`, or `headline`.
- `workbot/llm.py`: three structured OpenRouter tasks pinned to a tested provider endpoint with local schema validation; area calls request low reasoning, impact and priority high. A strict JSON-schema request does not prove the provider enforces local cross-field rules. `model_call_summary` diagnostics are logger-only and allowlisted: never log prompts, provider text, validation inputs, exception messages, identities, IDs, or secrets, and never add this metadata to cards, sessions, or priority inputs.
- `workbot/storage.py`: SQLite schema, visibility helpers, sources, and the dependency snapshot that makes a stored card fail closed on reload when its evidence changes.
- `workbot/seed.py` loads the synthetic company from `workbot/fixture/`: `directory.json` (org units, people, managers, team remits, responsibilities, each claim with its own source and visibility) and `records.json` (work records with person links). The fixture is deliberately built around topic clusters with hard cases (adjacent topics, expired duties, departed or moved people, mention-only links, restricted-only people, a team with no relevant trace) plus unrelated background records. When editing it, keep every text within 400 characters, never name a person in a record without linking them, and keep people known only through restricted sources free of any visible footprint; `tests/test_fixture.py` enforces these. `tests/unit_seed.py` is a separate nine-person dataset used only by the workflow and search unit tests.
- `workbot/templates/`: English server-rendered UI. `base.html` holds the shared layout and the simulation disclaimer; `home.html` is the prompt plus the list of earlier ideas; `session.html` renders the request as a conversation (idea, clarifications, progress, plan, collapsed full list); `source.html` shows one cited record.
- `tests/test_workflow.py`: session states, evidence audits, and visibility rules; `tests/test_search_and_ui.py`: hybrid search and HTTP flow; `tests/test_llm.py`: model request/response contracts and diagnostics; `tests/test_questions.py`: neutral question registry; `tests/test_plan.py`: the first-conversations plan; `tests/test_fixture.py`: validity of the shipped fixture. All are offline.
- `docs/competition/`: `rules.md` is a local extract (the live rules supersede it); `alexa.md` distinguishes the two Alexa+ routes; `submission.md` is the submission checklist; `judging.md`, `mini-challenges.md`, and `prizes.md` cover the rest.

## Working with the user and other agents

- Inspect the working tree and relevant tests before editing; preserve existing user changes.
- If the request, scope, or intended behavior is unclear, **ask the user before proceeding rather than guessing**. Do not silently turn a design-draft idea into current behavior.
- The user's quality goal is **no obvious errors**, not resolving every edge case, and the aim is to win the competition. Prefer fixes that remove visible mistakes over further calibration of debatable cases.
- Keep the repository small. Do not add experiment logs, dated reports, or preserved artifacts to the tree unless the user asks; delete superseded material instead of archiving it in place.
- Delegation is optional. Communicate with subagents in English and integrate and verify their findings yourself.

## Validation and documentation upkeep

- Start with tests relevant to the change. For Python changes, use `ruff check workbot tests` and `ruff format --check workbot tests`; if formatting is needed, run `ruff format` only on the affected files. Run these from an activated Python 3.12 environment with `requirements.txt` installed, or prefix them with `uv run --python 3.12 --no-project --with-requirements requirements.txt`, for example `uv run --python 3.12 --no-project --with-requirements requirements.txt python -m pytest -q`. Run `git diff --check` after edits. Offline stub tests do not certify live model quality.
- **With every relevant code change, review `README.md`, this file, and `docs/handoff.md` and update them in the same change when needed.** Keep human setup, behavior, and limitations in README; keep agent workflow and code guidance here. Do not make unrelated documentation edits merely to touch these files.
- Write Markdown as one logical line per bullet or paragraph; do not manually hard-wrap prose at a fixed column.
