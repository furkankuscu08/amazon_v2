## Product and language boundaries

- WorkBot is a **synthetic, simulated Alexa+ web experience**, not an official Alexa+ integration and uses no Alexa API; Amazon Bedrock serves only as the model provider. It shows consultation areas, evidence-backed people and roles, what to find out in each area, and uncertainty; it does not send messages, create invitations, or record coordination.
- Do not claim real identity or permission controls, production security or scale, or exhaustive stakeholder discovery. Preserve visibility checks: restricted sources and people known only through them must not enter accessible search, model context, cards, source views, or user-visible signals.
- Preserve the three model task types (impact, per-area evaluation, card-wide priority) and at most two sequential clarifications. The priority call orders areas and may pick up to four already-audited people to talk to first; it must never add a person or change a role. A missing or over-long choice is tolerated so it cannot discard the area order. Keep `mapping_unresolved`, `not_found`, `review_incomplete`, and request-level refusal distinct. Follow-up questions about a plan call no model: on 19 October 2026 the user chose rule matching and answers built from the plan over a fourth, selection-only model task, so keep them that way unless the user decides otherwise.
- **English is the WorkBot operational language.** Write demo ideas and clarification answers, synthetic work records, search intents, model prompts and requested responses, UI copy, and displayed questions/cards in English. Keep `README.md` and this file in English. This is a product convention, **not** a claim that the application detects or rejects other languages at runtime.
- Use synthetic inputs only. Never include `.env` secrets in code, logs, tool output, or commits. Live model calls (Amazon Bedrock, or OpenRouter when selected) transmit prompts and incur cost; run them only when the user explicitly approves a live test and its budget, and distinguish their results from offline tests. Submitting an idea through the web UI is a live call, and so is pressing **Listen**, or letting a newly arrived question, plan, or follow-up answer be read aloud (on unless the visitor turns it off), which sends the shown text to Amazon Polly, or using **Speak**, which sends the recording to Amazon Nova 2 Sonic on Bedrock.

## Repository map

`workbot/` is the application package, `tests/` contains offline regression tests, and `docs/` holds the design draft and competition research.

- `LICENSE` is MIT (copyright holder: Furkan). Keep it at the repository root so GitHub detects it.
- `compose.yaml` runs local Qdrant and, optionally, the app, built from the `Dockerfile` (non-root, with the embedding model downloaded at build time; `.dockerignore` keeps `.env`, `data/`, and `.git` out of the build context); `.env.example` is the configuration template. `deploy/` is the optional hosted demo: `workbot-ec2.yaml` is a CloudFormation template for one EC2 server whose instance role may only invoke Nova 2 Lite and Nova 2 Sonic and call Polly, and `compose.yaml` runs Caddy, the app, and Qdrant there, publishing only Caddy's ports; the app trusts forwarded headers from any address only because nothing else can reach it, so never publish the app's or Qdrant's port in that file. Keep that role's permissions in step with what the code calls. `requirements.in` lists direct dependencies; `requirements.txt` is the compiled Python 3.12 lock.
- `workbot/main.py`: FastAPI routes and the server-rendered flow. `POST /sessions` and `POST /sessions/{sid}/answer` store the request, start the workflow on a background thread with its own database connection, and redirect at once; the session page shows progress while the state is `processing`. Only a newly created session starts a run, so a repeated idempotency key cannot start a second one. Two optional hosted-demo guards live here too: the `access_gate` middleware sends every path except `/access` there until the visitor holds the cookie for `WORKBOT_ACCESS_CODE` (an HMAC of the code, never the code; every attempt is rate-limited before the comparison, `next` only accepts a path on this site, and a bad `WORKBOT_DAILY_IDEAS` stops new ideas with a 503), and `_create` takes one of `WORKBOT_DAILY_IDEAS` from the `daily_ideas` table per UTC day before a new session is stored, returning it if nothing new was stored; a known idempotency key is never counted. Both are off when unset, and neither is real authentication. `POST /sessions/{sid}/ask` answers a follow-up question about a valid plan by rendering the session page (200, no redirect) with the conversation; the earlier questions come back with the form as `prior-0` to `prior-4`, so nothing is stored and one visitor's questions never reach another on the shared hosted plans. Keep it that way: do not store follow-ups. It needs a `card` session (409 otherwise) whose card is still valid (410 otherwise), and questions of 1 to 200 characters. A new idea, and an answer to a pending question, first call `Searcher.check`; a `SetupError` (Qdrant not answering, checked first because seeding needs it too, or stale or missing seed data) renders `setup.html` with status 503 before anything is stored or sent to the model. Its message and command must stay plain setup advice.
- `workbot/models.py`: strict structured-output models. Each `Area` carries a `consultation_need`; each `PersonProposal` carries a `primary_evidence_id` (must be one of its citations), a required 5-600-character `contribution` (the prompt asks for under 250; the cap is higher so a provider enforcing it does not cut a sentence; the prompt asks for it before the role, and the card never stores it; on 19 October 2026 it was kept in the schema so the model still writes it before choosing the role, because removing it untested so close to the deadline risked a regression with no visible gain), and a `relevance` of `direct`/`adjacent`/`weak`. The model writes no question or caution text for a person. The direct-contact evidence requirement lives in the audit, not the schema, so one inconsistent role field cannot void a whole area review.
- `workbot/service.py`: session orchestration, all of an idea's per-area model calls at once (six worker threads), the deterministic evidence audit, card states, and the in-memory progress shown on the waiting page. `run` calls the three model tasks in order as `_ask_impact`, `_review_areas`, and `_apply_priority`. Progress may hold only a stage and area labels with a done flag, never people, sources, counts, or diagnostics. A live run has a progress entry from before its session becomes `processing` until after it leaves that state; the session page relies on this to close a `processing` session without one as a refusal, so keep that ordering and a single app process. Keep SQLite/search/permission reads and audits on the thread that runs the workflow; only independent area model requests belong in workers. Wait for all areas before the priority call, keep area failures isolated as `review_incomplete`, and check the shared question before reordering so a guard error leaves the original order intact. A `direct_contact` needs `relevance=direct` plus a strong work or current-responsibility tie on the single primary source; `adjacent`/`weak` proposals are kept as advisors; an advisor's primary source must itself be a work, reporter, or current-responsibility tie; `mention`-only evidence is not proposed; a routing contact needs both current manager and visible remit evidence and is hidden when a direct contact exists or a direct proposal was broken. A *broken* direct proposal names a person or source outside the candidate pool, an inactive person or one in another team, a source no longer visible or current, an uncited primary, or a repeated citation; it marks the review unreliable (`review_incomplete` when nobody else is left). An *overclaimed* one rests on real evidence that does not show direct work, or carries the model's own `adjacent`/`weak` relevance: it becomes an advisor when its primary source is an advisor tie and is dropped otherwise. Because the prompt asks for a routing contact only when there is no direct contact, an overclaim that leaves no direct or routing contact makes the audit add the pool's single current manager with a visible remit from the directory. A review in which the model proposed nobody stays `not_found`. The audit verifies visibility and link strength, **not** whether the source is semantically relevant to the area. The model's `contribution` is never put on the card, shown, or passed on (shown as an unverified summary, it once called a policy "in force at that time" the current one). The priority call receives the idea, the clarification answers (as the impact and area calls do), and the areas. Neither the `ended_duty` note nor its `context_ids` may be passed to the priority call, and `_priority_areas` also removes the area's rejection flags. The card carries no per-person question or caution text: the plan shows the area's `consultation_need` as what to find out, and one fixed caution closes the full list. Evidence lines in `why` name no source ID; they are written primary source first, then the other citations in `evidence_ids` order, and `plan.py` relies on that order to link each line. A skipped clarification ends the question budget. The impact prompt says most ideas need no clarification and allows one only when the areas cannot be told without it (never for amounts, dates, or other details that do not change the areas), keeps it on the idea itself (what changes, which process or product, who it affects), and forbids asking which reviews, approvals, laws or rules, compliance checks, teams, systems, or owners the idea needs or involves, who handles something today, or repeating an answered question. It reserves `mapping_unresolved` for an area no supplied org unit fits: being unsure whether the idea affects an area, or a skipped question, is not a reason (the older "valid but uncertain area" wording made live runs leave Legal and Compliance without a team after a skipped compliance question in 14 of 15 runs); it asks for a `consultation_need` under 110 characters and the priority prompt for a shared question under 160, as prompt requests only, so do not tighten the schema caps to match. The audit also attaches an `ended_duty` note when an accepted person has a visible responsibility that has ended and shares a word with the area (its label, its `consultation_need`, or its keyword search intents; the short need alone lost the words in live runs), unless they hold a current one that also does; the model never sees expired duties, and the note's source is listed in `context_ids` so the dependency snapshot fails the card closed if that source changes or stops being visible. A routing contact's plan line states that no one was identified from the visible work, or that no direct contact was established when an advisor is shown in the same area; it must not claim the search found nothing, because retrieval always returns records. That line is built from the manager and remit records, so the plan never links it to the primary source; the full list links each of its sources. Never place diagnostic or rejection details in the card passed to priority.
- `workbot/search.py`: visible BM25/Qdrant retrieval fused by reciprocal rank, keeping per intent only records both channels returned plus each channel's top three (at most eight per area), and candidate selection from work links, current visible responsibilities, and manager plus remit. The ten work-link candidates are chosen by link strength and then by the retrieval rank of their best record; mention-only people are not work candidates. A title match without visible evidence must not expose a restricted-only person to model context.
- `workbot/plan.py`: pure functions that turn a stored card into the short plan at the top of the page. It also builds `headline`, `lead`, and `spoken` (their concatenation, then `invite`, a fixed line asking for follow-up questions when the plan names someone), the plan summary that the page shows in its "Alexa says" panel and **Listen** reads aloud; build them only from plan data (names, home areas, a routing contact's role, the role and month of an `ended_duty` note, the count of areas in `more`, and the open-area count), never from model prose, so the voice cannot say more than the panel. Each person gets one home area (where their role is strongest; between equal roles, their own team's area); the plan lists the priority call's `first_conversations` or, without a usable choice, the strongest person of each area (preferring one without an `ended_duty` note); other areas show a one-line cross-reference, and an `ended_duty` note found in any area is shown with the person in their home area. Each plan entry also carries `short`, the plan line: a work record's headline is rewritten as a verb and record kind ("Wrote a document: ‘…’") and its quote cut to the first sentence when the stored excerpt holds one (a period after an abbreviation such as "e.g." or "Dr." does not end a sentence); any other line is unchanged; `ended_short`, the ended-duty note as role and month ("Approver role ended in June 2025.", as the voice says it); and `ended_full`, the whole note for the full list with its date written out. The full list's evidence lines are rewritten the same way at render time ("Assignee of jira record on 2026-03-02: ‘…’" becomes "Assigned to a Jira issue on 2 March 2026: ‘…’"), so stored cards read the same; a line that does not match is left alone. `groups` puts the chosen people under their home area with its consultation need, ordered by each area's first chosen person and keeping the chosen order inside an area, except that a person with an `ended_duty` note follows the others in their area and a group of only such people follows the other groups (this reorders, never adds or drops; `first` and the spoken text follow the same order); each entry also carries `initials` for the avatar. `more` names each area with people where no chosen person has their home and someone was left out, with the people left out there in `order`'s order; gaps stay in `gaps`. `order` lists each area's people for the full list: those shown in full there before the cross-references, and in each part the plan's people first in its order, then the others in card order (it only reorders). `people` holds everyone on the card once, with the role label and the evidence lines paired with their sources, so the full list uses the same labels as the plan and shows links instead of source IDs. It is computed at render time and must tolerate older cards without `org_id`, `team`, `primary_kind`, `headline`, or `primary_evidence_id`, and ones whose evidence lines still end with a bracketed source ID.
- `workbot/followup.py`: pure functions that answer follow-up questions from a built plan and its card, with no model. `resolve` matches a question by rules to a kind (`why`, `prep`, `others`, `open`, `ambiguous`, `unlisted`, `help`) and to people on the card only (exact name words, then near matches for a misheard name, allowed only for a capitalized word with the same first letter and length within one, never for an area or team word or a listed common word; `unlisted` needs a capitalized, non-acronym word that does not start a sentence); `reply` builds the answer only from text the page shows (names, areas, role labels, plan lines, ended-duty notes, "What to find out", the shared question, open areas), so the panel and the voice say the same thing and say nothing new; `why` and `prep` say the plan line with the person as its subject ("Omar wrote a document: …", "Tara Reed is the current reviewer — …"; `_said`, which leaves any other line as written) and link its source as the card does, and `prep` starts with that line before what to ask; `chips` suggests up to four questions that fit the plan. A name not on the card must get the same answer whoever it belongs to, and no reply may repeat the question, so a person known only through restricted sources cannot be told apart from one who does not exist.
- `workbot/llm.py`: the three structured tasks behind one `complete(task, payload)` interface, on two providers that share the call log and local schema validation. `Bedrock` (the default from `default_model()`) calls the Converse API on `WORKBOT_BEDROCK_MODEL` (default `global.amazon.nova-2-lite-v1:0`) with credentials from the standard AWS chain and `AWS_REGION` passed explicitly, because boto3 reads only `AWS_DEFAULT_REGION`. Nova 2 Lite rejects `outputConfig` and `strict` tools, so each task forces a single tool whose input schema is the task's Pydantic schema; only the local validation enforces it, and a reply is accepted only with `stopReason` `tool_use` and exactly one call of that tool. Extended thinking is low for all three tasks: medium spent up to the whole 8,192-token cap on reasoning in live runs, and high effort forbids the cap. `OpenRouter` (selected by `WORKBOT_MODEL_PROVIDER=openrouter`) is pinned to a tested provider endpoint with strict JSON-schema output; area calls request low reasoning, impact and priority high. A strict JSON-schema request does not prove the provider enforces local cross-field rules. Missing AWS credentials, profile, or Region, a missing OpenRouter key, or an unknown `WORKBOT_MODEL_PROVIDER` fails as `not_configured` before any prompt is sent; other AWS sign-in errors keep their class name. botocore, and the `smithy_*` and `aws_sdk_*` loggers of the Sonic SDK, log whole requests at `DEBUG` (prompts, audio, transcripts), so never enable that level for them. A reply that fails local validation, or ends without an answer for a reason other than the output cap, is requested once more (`_Unusable`); a cut-off reply, one whose input exceeded the context window, a service error, an unexpected response shape, or missing setup is not repeated. Each request writes one `model_call_summary` log line (task, provider, attempt, outcome, error class name or WorkBot's own fixed code, stop reason from a fixed allowlist, Pydantic validation error codes, HTTP status, truncation flag, duration, token counts). Keep it to fixed codes and numbers: never log prompts, provider text, validation inputs, messages of exceptions WorkBot did not raise itself, identities, IDs, or secrets, and never add this metadata to cards, sessions, or priority inputs.
- `workbot/speech.py`: Amazon Polly for **Listen**: `Speech.audio(text)` synthesizes mp3 with the standard voice (`WORKBOT_POLLY_VOICE`, `WORKBOT_POLLY_ENGINE`) in `AWS_REGION`, keeps the last 64 texts in memory, and raises `SpeechError` with a plain message; it logs only the exception class. `main.py`'s `/sessions/{sid}/speech.mp3` reads the valid card's `plan.spoken` or the pending question ("One clarification before searching. …") and nothing else; a stale card, a refusal, or a running request has nothing to read (404), and a Polly failure is a 503 with that plain message. `/sessions/{sid}/reply.mp3?q=…` reads the follow-up answer `followup.reply` builds for that question on a valid card; the question chooses the answer and is never sent to Polly, and it is limited per address (`reply_limiter`).
- `workbot/transcribe.py`: speech to text for **Speak** with Amazon Nova 2 Sonic over Bedrock's bidirectional stream, through the `aws-sdk-bedrock-runtime` SDK with its CRT transport (boto3 has no bidirectional streaming, the SDK's default aiohttp transport cannot stream both ways, and Amazon Transcribe is not open to this account). It keeps only Sonic's `textOutput` for the USER role, across every user turn of the recording (a pause can split it), and stops 1.5 s after the last user text or 8 s after sending with none. `Transcriber.text(pcm)` takes 16 kHz 16-bit mono PCM of at most 20 seconds, gets credentials and Region from boto3's chain like the model calls (so the test setup also keeps it offline), times out after 30 seconds, closes the stream and transport within 2 seconds, logs only the exception class, and raises `TranscriptionError` with a plain message. `POST /transcribe` (same-origin, `application/octet-stream`, size-capped while reading, rate-limited per address) returns JSON `{"text"}` or `{"error"}`; the text only fills the box and never starts a run. The browser side is the Speak part of `templates/_script.html`.
- `workbot/storage.py`: SQLite schema, visibility helpers, sources, and the dependency snapshot that makes a stored card fail closed on reload when its evidence changes.
- `workbot/seed.py` loads the synthetic company from `workbot/fixture/`: `directory.json` (org units, people, managers, team remits, responsibilities, each claim with its own source and visibility) and `records.json` (work records with person links). The fixture is deliberately built around topic clusters with hard cases (adjacent topics, expired duties, departed or moved people, mention-only links, restricted-only people, a team with no relevant trace) plus unrelated background records. Anders Holm's tie to spending-policy changes is a directory responsibility only: a work record about reviewing that policy, worded like Omar's 2024 budget approval policy, made live runs on 19 October 2026 pass over Omar and his ended-role note, so do not add one back. When editing it, keep every text within 400 characters, never name a person in a record without linking them, and keep people known only through restricted sources free of any visible footprint; `tests/test_fixture.py` enforces these. `tests/unit_seed.py` is a separate nine-person dataset used only by the workflow and search unit tests.
- `workbot/templates/`: English server-rendered UI with a single light theme. `base.html` holds the only stylesheet (inline, plain CSS with custom properties; no framework, build step, or web font), the inline SVG favicon (a plum square matching the wordmark, so no `/favicon.ico` request), the wordmark, the simulation disclaimer, the `#page` wrapper around each page's content, and, after it, `_script.html`, the only script, which every page shares. It runs `setup(root)` on the page and on every page it swaps in, so its code must not assume a fresh document, and no template may put a `<script>` inside `#page`. Forms marked `data-swap` (the idea, the answer, the skip, the follow-up box, and each suggestion chip) are sent with `fetch` and the page they lead to replaces `#page` in place (`history.pushState` when the address changes; a native submission when anything goes wrong), and the waiting page swaps its result in the same way; this keeps the sound a visitor allowed by clicking. A swap removes parsed `<noscript>` elements (their refresh would fire) and stops audio, older polls, and any recording. Only a question, plan, or follow-up answer that arrives through a swap is read aloud on its own (the newest answer's **Listen** carries `data-speech-auto`, and the swap reads and scrolls to it instead of the plan), and only on a page the visitor has clicked; see README for the rest of the behavior. `home.html` is the prompt, three example buttons that only fill the idea box (shown by script, never submitting; each must be an idea in `tests/expectations.json`, which `tests/test_fixture.py` checks, and pickup lockers was replaced by customer scoring on 19 October 2026 because its fixture has no relevant record by design and live runs kept proposing unrelated direct contacts), the "Read answers aloud" checkbox (shown by script, with no `name`, so it is never sent), and the list of earlier ideas; `session.html` renders the idea, any clarifications, then one state (the question and the plan carry a **Listen** button, shown only by script, that plays `GET /sessions/{sid}/speech.mp3`; each follow-up answer's plays `reply.mp3`): progress (polled one request at a time, with a lost-connection line on failure and a full reload when a reply holds no `#page`), a question (in the same dark panel as the plan, labelled "Alexa asks"; answered questions are listed as "Alexa asked"), a refusal, an out-of-date notice, or the plan (the "Alexa says" panel, then the follow-up conversation with each "Maya asked" question and its "Alexa says" answer, the suggestion chips, each its own small form carrying the earlier questions, and the follow-up box with **Speak**; then one card per area with its "What to find out" and its chosen people, a line naming the areas in `more`, the shared question, "Still open" gaps, and the collapsed full list with one collapsible section per area, which shows each area's "What to find out" but not the impact model's `rationale` or `mapping_reason`: an area without a team gets the fixed line "Team not identified. ## Working with the user and other agents

- Inspect the working tree and relevant tests before editing; preserve existing user changes.
- If the request, scope, or intended behavior is unclear, **ask the user before proceeding rather than guessing**. Do not silently turn a design-draft idea into current behavior.
- The user's quality goal is **no obvious errors**, not resolving every edge case, and the aim is to win the competition. Prefer fixes that remove visible mistakes over further calibration of debatable cases.
- Keep the repository small. Do not add experiment logs, dated reports, or preserved artifacts to the tree unless the user asks; delete superseded material instead of archiving it in place (the design draft in `docs/archive/` is kept on purpose).
- Delegation is optional. Communicate with subagents in English and integrate and verify their findings yourself.

## Validation and documentation upkeep

- Start with tests relevant to the change. For Python changes, use `ruff check workbot tests conftest.py` and `ruff format --check workbot tests conftest.py`; if formatting is needed, run `ruff format` only on the affected files. Run these with the repository's `.venv` (Python 3.12 with `requirements.txt` installed, created as in the README's Setup): activate it, or call its tools directly, for example `.venv/bin/python -m pytest -q` and `.venv/bin/ruff check workbot tests conftest.py`. Only when there is no `.venv`, prefix the commands with `uv run --python 3.12 --no-project --with-requirements requirements.txt` instead; do not create or delete the `.venv` without asking. Run `git diff --check` after edits. Offline stub tests do not certify live model quality.
- **With every relevant code change, review `README.md` and this file and update them in the same change when needed.** Keep human setup, behavior, and limitations in README; keep agent workflow and code guidance here. Do not make unrelated documentation edits merely to touch these files.
- After finishing an implementation and before opening a pull request, review your own diff as a reviewer would: correctness, leftover references, weakened tests, and documentation that no longer matches. Fix what you find and tell the user what the review found.
- Write Markdown as one logical line per bullet or paragraph; do not manually hard-wrap prose at a fixed column.
